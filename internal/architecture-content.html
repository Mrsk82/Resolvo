Resolvo

How Resolvo is built

Resolvo is customer support software for small Indian brands. One server holds many separate workspaces; each workspace is one customer brand with its own people, tickets and settings.

Three ideas to hold on to

  • One server, many workspaces. Everything runs in one Node process. Each workspace reads and writes only its own database file.
  • The owner is separate from every workspace. The owner session can see everything through the Owner Console but cannot call workspace functions; workspace users can never reach owner tools.
  • No build step. The app is plain JavaScript and CSS served as files. What is in the folder is what runs.

Control hierarchy

Who controls what

Three levels of people, and customers who never sign in.

LEVEL 1

Platform owner

One account (you). Signs in at the Owner Console. Creates, pauses and deletes workspaces, changes plans and feature switches, reads the audit log, runs backups, sees website growth. Owner sessions are refused by /api/call.

LEVEL 2

Workspace (a brand)

Has a slug, a plan (Free, Trial, Pro or Enterprise), limits (for example the number of users, 20 unless raised), feature overrides and a status: pending until the sign-up email is verified, then active.

LEVEL 3

People in a workspace

Roles: Admin, Manager, Agent, Developer, QA. Admins manage users and settings. Each person has a ticket limit (default 10), a skill, and an available/away status that the queue respects.

OUTSIDE

Customers

Do not sign in to the app. They reach a workspace by email, WhatsApp, the embeddable widget, the public ticket form, or the self-service portal (Enterprise).

Protection for the owner registryA guard puts back any workspace that goes missing from owner.json by mistake, and deletes only happen when a slug is named explicitly. Deleted workspaces go to a 30-day recycle bin first.

Customer journey

What a brand goes through

From the website to a first answered ticket. These are the same steps the Growth tab measures.

  1. Visit and sign upA public page counts a cookie-free visit. The sign-up form saves where the person came from with the request.
  2. Verify the emailThe workspace is pending until the link in the email is used (valid for 48 hours; a new link is sent if they try again). Then it becomes active.
  3. 14-day TrialA trial gives Pro features except the Enterprise-only ones. After it, the workspace moves to Free unless they pick Pro or Enterprise.
  4. Connect a channelGmail (OAuth, with push), another mailbox over IMAP, WhatsApp through Twilio or Meta Cloud, the widget, or the public ticket form.
  5. Work ticketsMessages become tickets with a priority and a response target. The queue can assign them. Agents reply from the web or phone app; AI can draft a reply that a person reviews.
  6. Stay with itReminders, nudges, reports and a daily digest keep people coming back. The Growth funnel counts "still using it a week later".

Prices per brand per month: Free ₹0, Pro ₹999, Enterprise ₹2,499 (no per-agent charge).

Plans and feature switches

Each plan is a set of on/off switches. The owner can override a switch for one workspace without changing its plan.

How a workspace's switches are worked out: start from the plan's set, apply any default changes the owner made, then apply that workspace's own overrides. The table below is read from the running server, so it is always the real list.

API

API and routes

In-app functions

POST /api/call with a function name and arguments. Needs a workspace session. Admin-only functions check the role inside.

Owner tools

/api/owner/…. Need an owner session (ownerOnly): workspaces, data browser, monitor, backups, recycle bin, site settings, growth, this page.

Public endpoints

Sign-up, demo request, contact, visit beacon (/api/hit), public ticket create, widget script, WhatsApp webhook, site config. Rate-limited; forms are escaped before they become email.

Sign-in

POST /api/login returns a session token sent back as the x-session-token header. Owner sessions last 30 days; workspace sessions 8 hours or 30 days.

Flows

Key flows

An email becomes a ticket

  1. ArrivesGmail pushes the message to Resolvo, or the poller fetches it (every 2 minutes, only for mailboxes not on Gmail push).
  2. De-duplicatedThe message id is checked against processed_email_ids so nothing is imported twice.
  3. Ticket madeA new thread becomes a ticket; a reply in an existing thread is added to it. If email triage is on, AI suggests priority and category.
  4. AssignedThe queue engine picks a person (next section). Push notifications go out.
  5. AnsweredThe agent replies (optionally from an AI draft). The reply is sent from the workspace's own mailbox.

A new brand signs up

  1. FormRate-limited, checked with Turnstile, reserved and test addresses refused.
  2. Pending workspaceCreated with its attribution (campaign, source) and a verify link.
  3. VerifiedThe link activates the workspace and its first Admin. Nurture emails then go out on day 1, 3, 7 and 14.

Shopify order lookup

Inside a ticket the agent can look up the customer's order from the connected Shopify store (read-only lookup, tested against a fake store).

WhatsApp

Twilio or Meta Cloud posts the message to /api/whatsapp/webhook; it becomes or joins a ticket; replies go back through the same provider.

Queue

Queue engine: who gets the next ticket

Runs when a ticket arrives and the workspace has the queue switched on. First rule that finds someone available wins.

  1. Frozen?If the queue is frozen, nobody is assigned.
  2. Routing rulesRules by keyword in the subject, sender's domain, exact sender, or priority. A match assigns to the named person if they are active, not away, and under their ticket limit.
  3. Critical priorityIf priority routing is on, a Critical ticket goes to the person in the queue with the most free capacity.
  4. Time rulesRules for hours of the day assign to a named person during those hours.
  5. Round robinOtherwise the next person in the queue who is available and under their limit.

Capacity is the person's ticket limit minus their open tickets (resolved and closed do not count).

Email

Email system

Resolvo's own email

Sign-up verification, password reset, welcome and nurture messages, the Monday growth digest and owner alerts. Sent from the server's mailbox. If it is off, the Owner Console health tab and a banner say so.

Each brand's email

Replies to customers go from the brand's own connected mailbox (Gmail OAuth or SMTP/IMAP settings), so customers see the brand, not Resolvo.

Safe in tests

With MAIL_CAPTURE set, every email is written to a file instead of being sent. All automatic tests use it.

No reply loops

Automatic messages carry auto-reply headers so another helpdesk does not answer them.

One rule when testingAlways blank EMAIL_USER and EMAIL_PASS for a test server copy. The contact form used to send real mail through those settings even in tests; it now honours MAIL_CAPTURE.

Security

Security

Sign-in

Hashed passwords (bcrypt). Session tokens in a header, not cookies. Two-factor sign-in is a Pro switch.

Separation

Each workspace has its own database file. Owner and workspace sessions cannot call each other's routes.

Public forms

Rate limits, length limits, Turnstile on sign-up, escaped HTML in emails to the owner, reserved and test addresses refused.

Secrets

Hashes, tokens and keys are removed on the server before the Owner Console sees them. Social-channel tokens are stored encrypted. Secrets are never in git.

Recovery

Nightly backups, a 30-day recycle bin, a guard against missing workspaces, and an audit trail of owner actions.

Privacy of the website

Google Analytics only after the visitor accepts. Visit counts are cookie-free and store no IP address; the app itself is not counted.

Known limitsContent-Security-Policy is off (the app uses inline scripts). Workspace sessions live in server memory, so a restart signs everyone out. No SOC 2 or ISO 27001 certification; the public Security page says so.

Phone

Phone app and phone screen

  • The Android app is the same web app inside a Capacitor shell. Its project and release key are kept outside this repository.
  • On a phone the web app switches to a phone layout with larger tap targets and screens arranged for one hand.
  • Push notifications through web push, with buttons that act on one ticket and pass through the normal permission checks.
  • Phone extras: an outbox that holds replies sent while offline, voice dictation, photos in replies, an app lock, and a home-screen widget.
  • Download counts are kept in data/app_downloads.json; the website's /app page links to the download.

Website

Website and growth tracking

  • Pages: static HTML in public/, generated or checked by scripts/build-site-pages.py, seo-pass.py and make-og-images.py. The sitemap lists every public page, and the Site map page in the footer links to all of them.
  • Site script: public/js/site.js handles the cookie choice, the WhatsApp button (number set in Owner Console), tagged-link capture and the visit beacon.
  • Counting: lib/analytics.js. Cookie-free, no IP stored, bots and app pages ignored, a daily-rotating salted hash for "visitors per day".
  • Leads: every sign-up, demo, design-partner application and contact message is logged with source, medium and campaign (owner.leadLog).
  • Owner Console, Growth tab: visits, sources, funnel (signed up, activated, channel connected, first reply, active after 7 days), stuck workspaces, tagged-link builder, Monday email.
  • Free tools: support calculator, SLA calculator, WhatsApp template generator. Guides for set-up and posting are in docs/growth/.

Operations

Deploying, backups and tests

Deploy

  1. Commit and pushStage explicit paths only (never git add .) and push to main on GitHub.
  2. Server pullsOver SSH: git pull origin main, npm install --omit=dev, pm2 restart resolvo.
  3. CheckOpen the app and this page: the commit shown in the top bar should be the one just pushed.

Tests

Suites live in docs/ui-redesign/tools/ and run a throwaway copy of the app on their own port with mail captured, so nothing real is touched. Covered: website audit, Owner Console, owner portal and delete, safeguards (backups, recycle bin), phone layout and features, first-customer fixes, Shopify, growth tracking, SEO pages.

Backups and monitoring

Nightly at 03:30. The Owner Console health tab shows the last backup, size and history. Memory spikes, restarts and failures email the owner.
